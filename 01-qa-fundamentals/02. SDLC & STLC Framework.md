
# 🔄 SDLC & STLC Framework

> **วัตถุประสงค์:** เข้าใจวงจรการพัฒนาซอฟต์แวร์ (SDLC) และวงจรการทดสอบ (STLC) เพื่อทำงาน QA อย่างมีระบบและเป็นมืออาชีพ

---

### 🏗️ 1. SDLC (Software Development Life Cycle) 

วงจรชีวิตการสร้างซอฟต์แวร์ มุ่งเน้นไปที่ **"การผลิต"** ตั้งแต่เริ่มต้นจนส่งมอบระบบ

* **เป้าหมาย:** ผลิตซอฟต์แวร์คุณภาพสูง ตรงตามความต้องการ ภายใต้งบประมาณและเวลาที่กำหนด
    
- **กระบวนการหลัก:**
    
    1. **Requirement Analysis:** รวบรวมและวิเคราะห์ความต้องการจากลูกค้า
        
    2. **Design:** ออกแบบสถาปัตยกรรมระบบ (System Architecture) และหน้าจอ (UI/UX)
        
    3. **Development (Coding):** เขียนโปรแกรมจริงโดย Developer
        
    4. **Testing:** ตรวจสอบความถูกต้องของระบบ *(ขั้นตอนนี้คือพื้นที่ทำงานหลักของ STLC)*
        
    5. **Deployment:** ติดตั้งซอฟต์แวร์ให้ผู้ใช้งานจริง
        
    6. **Maintenance:** บำรุงรักษาและแก้ไขหลังการใช้งาน
        

--- 
### 🧪 2. STLC (Software Testing Life Cycle) 
วงจรการ **"ตรวจสอบคุณภาพ"** ที่รันควบคู่ไปกับ SDLC เพื่อให้ซอฟต์แวร์มีคุณภาพสูงสุด 
#### 📊 สรุป STLC 6 ขั้นตอน 

|         | ขั้นตอน                 | จุดประสงค์                  | Input           | Output                 |
| :-----: | :---------------------- | :-------------------------- | :-------------- | :--------------------- |
| **1️⃣** | **Req. Analysis**       | วิเคราะห์หาจุดกำกวม / Gaps  | Requirement Doc | Testable Requirements  |
| **2️⃣** | **Test Planning**       | วางกลยุทธ์, Scope และ Risk  | Requirements    | Test Plan              |
| **3️⃣** | **Test Design**         | ออกแบบเคส (EP/BVA/RTM)      | Requirements    | Test Cases + Test Data |
| **4️⃣** | **Test Implementation** | เตรียม Environment และ Data | Test Cases      | Environment Ready      |
| **5️⃣** | **Test Execution**      | รัน Test และแจ้ง Bug        | Test Cases      | Test Results + Bugs    |
| **6️⃣** | **Test Closure**        | สรุปผล และถอดบทเรียน        | Test Results    | Test Summary Report    |

### 🎯 เจาะลึกรายขั้นตอน (ตัวอย่าง: ระบบจองที่จอดรถล่วงหน้า) 
#### 1️⃣ Requirement Analysis (วิเคราะห์ความต้องการ) 
* **QA ตั้งคำถาม:** *"ถ้าจองวันที่ 8 ได้ไหม? ถ้าจะยกเลิกต้องยกเลิกก่อนกี่ชั่วโมง?"* (เริ่มหาจุดกำกวม) 
* **เหตุผล:** ถ้าสเปคผิดพลาดตั้งแต่นี้ Test Case ก็จะผิดตาม → ต้องดักจับปัญหาให้เร็วที่สุด! 
#### 2️⃣ Test Planning (วางแผนกลยุทธ์) 
* **Scope:** อะไรที่ต้องเทส (เช่น ระบบจองที่จอด, ระบบชำระเงิน) / อะไรที่ไม่ต้องเทส (เช่น ระบบสมัครสมาชิก - ทำเสร็จไปแล้ว) 
* **Strategy:** ใช้ Manual หรือ Automate? ใครรับผิดชอบส่วนไหน? 
* **Risk:** ถ้า Dev ส่งงานช้าจะปรับแผนอย่างไร? ถ้าไม่มี iPhone รุ่นเฉพาะจะใช้อะไรทดสอบแทน? 
* **Criteria:** กำหนดเงื่อนไขเริ่มเทส (**Entry Criteria**) และเงื่อนไขจบการเทส (**Exit Criteria**) 
#### 3️⃣ Test Design (ออกแบบ Test Case) 
* **วิเคราะห์ Scenario:** ออกแบบทั้ง **Positive** (จองได้สำเร็จ) และ **Negative** (กรอกข้อมูลผิด / จองเกินจำนวนวันที่กำหนด) 
* **เขียนรายละเอียด:** ระบุ ID, Description, Pre-conditions, Steps, Test Data, Expected Result 
* **Traceability Matrix (RTM):** สร้างตารางเช็คว่า *"ทุก Requirement มี Test Case ครอบคลุมแล้วหรือยัง?"* 

#### 4️⃣ Test Environment Setup (เตรียมระบบ) 
* **เตรียมระบบ:** Deploy ซอฟต์แวร์เวอร์ชันล่าสุดลง Server สำหรับการ Testing 
* **เตรียมฐานข้อมูล:** สร้าง Test User และข้อมูลเงินจำลองพร้อมสำหรับการทดสอบ 
* **Smoke Test:** ลองคลิกฟีเจอร์หลักเพื่อดูว่าระบบทำงานได้หรือไม่ หากพังตั้งแต่จุดนี้ให้ส่งกลับ Dev ทันที (ยังไม่รับมาเทสต่อ)

#### 5️⃣ Test Execution (ลงมือทดสอบ) 
* **รัน Test Case:** บันทึกผลลัพธ์เป็น Pass หรือ Fail 
* **แจ้งข้อบกพร่อง (Bug Report):** เมื่อพบปัญหา ให้แจ้ง Dev พร้อมระบุความรุนแรง (**Severity**) เช่น Blocker, Major 
* **Retest:** เมื่อ Dev แก้ไขบั๊กเสร็จแล้ว ต้องทดสอบซ้ำในจุดเดิมเพื่อยืนยันการแก้ไข 
* **Regression Test:** ทดสอบระบบในส่วนรอบข้างเพื่อเช็คว่าการแก้โค้ดกระทบให้ส่วนอื่นพังหรือไม่ 
#### 6️⃣ Test Closure (สรุปและปิดงาน) 
* **Exit Criteria Check:** ตรวจสอบว่าบั๊กระดับร้ายแรงถูกแก้ไขหมดแล้วหรือยัง? Test Case สำคัญรันครบหรือไม่? 
* **Test Summary Report:** สรุปผลการทดสอบภาพรวมให้ทีม เพื่อใช้ตัดสินใจ Go / No-Go 
* **Lesson Learned:** ถอดบทเรียนร่วมกับทีมเพื่อนำไปปรับปรุงกระบวนการใน Sprint ถัดไป

### 💡 Key Takeaways (จุดสำคัญ) 

* **STLC ≠ Waterfall:** ในระบบ Agile / Scrum กระบวนการ STLC จะรันเป็นลูปสั้นๆ ในทุก Sprint โดย QA ต้องเริ่มทำ Requirement Analysis ตั้งแต่วันแรก 
* **ขั้น 1–3 (Analysis & Design):** คือการ **"ใช้สมอง"** — วิเคราะห์สเปค ประเมินความเสี่ยง ออกแบบเคส 
* **ขั้น 4 (Implementation):** คือการ **"เตรียมระบบ"** — เซ็ต Environment และจัดเตรียมข้อมูล 
* **ขั้น 5 (Execution):** คือการ **"ลงสนามจริง"** — รัน Test บันทึกผล และ Log Bug 
* **ขั้น 6 (Closure):** คือการ **"สรุปและพัฒนา"** — วัดผลสำเร็จและปรับปรุงกระบวนการ
