# 🔍 04. Verification vs Validation

> **วัตถุประสงค์:** เข้าใจความแตกต่างระหว่างการตรวจสอบความถูกต้องตามข้อกำหนด (Verification) และการตรวจสอบความถูกต้องตามความต้องการของผู้ใช้จริง (Validation) เพื่อทำ QA ได้อย่างครอบคลุมทุกมิติ

---

## 🎯 1. นิยามสั้นๆ

* **Verification** (*"Are we building the product right?"*)
  > **"เราสร้างสินค้าได้ 'ถูกต้องตามแบบ' หรือไม่?"**  
  เน้นการตรวจสอบ **กระบวนการ** และ **เอกสาร/แบบร่าง** เพื่อให้แน่ใจว่างานที่ออกมาตรงตามสเปกที่ตกลงกันไว้ตั้งแต่แรก

* **Validation** (*"Are we building the right product?"*)
  > **"เราสร้างสินค้าที่ 'ใช่' สำหรับผู้ใช้จริงหรือไม่?"**  
  เน้นการตรวจสอบ **ตัวซอฟต์แวร์จริงที่รันได้** เพื่อให้แน่ใจว่าระบบทำงานได้ตอบโจทย์ธุรกิจและความต้องการของลูกค้าจริงๆ

---

## 🛠️ 2. กิจกรรมที่เกิดขึ้นในแต่ละด้าน

### 📄 Verification (Static Testing — ไม่รันโค้ด)
เป็นการตรวจสอบโดย **ไม่เปิดรันโปรแกรม** (มักทำในช่วงต้นของ STLC / Shift-Left)
* **Reviewing:** อ่าน Requirement Doc, Design Doc เพื่อหาจุดกำกวมหรือจุดผิดพลาดก่อนเริ่มเขียนโค้ด
* **Walkthrough:** ผู้สร้างงานนำเสนอโค้ด/เอกสารให้ทีมฟังแบบเป็นกันเองเพื่อหาข้อบกพร่องร่วมกัน
* **Inspection:** การตรวจทานอย่างเป็นทางการตาม Checklist และมาตรฐานขององค์กร

### 🧪 Validation (Dynamic Testing — รันซอฟต์แวร์จริง)
เป็นการตรวจสอบโดย **เปิดรันโปรแกรมจริง** (มักทำในช่วงกลางถึงปลายของ STLC)
* **Unit Testing:** ทดสอบโค้ดฟังก์ชันย่อยๆ โดย Developer
* **Integration Testing:** ทดสอบการเชื่อมต่อกันระหว่าง Module / API
* **System Testing:** ทดสอบระบบรวมทั้งหมดแบบ End-to-End โดย QA
* **User Acceptance Testing (UAT):** ให้ลูกค้า/ผู้ใช้จริงลองใช้งานเพื่อยืนยันความพึงพอใจ

---

## 📊 ตารางเปรียบเทียบเชิงลึก

| หัวข้อ            | Verification                                  | Validation                                               |
| :---------------- | :-------------------------------------------- | :------------------------------------------------------- |
| **คำถามหลัก**     | สร้างตามสเปกไหม? (*Build it right?*)          | สร้างสิ่งที่ลูกค้าต้องการไหม? (*Build the right thing?*) |
| **สิ่งที่ตรวจ**   | เอกสาร, แผนผัง, โค้ดร่าง (**Static Testing**) | ตัวซอฟต์แวร์ที่รันได้จริง (**Dynamic Testing**)          |
| **ผู้รับผิดชอบ**  | QA, Dev, BA (ช่วยกันรีวิวเอกสาร)              | QA และ ผู้ใช้งานจริง (*End User / Stakeholders*)         |
| **ช่วงเวลาที่ทำ** | เริ่มได้ทันทีตั้งแต่วันแรก (**Shift-Left**)   | ทำได้เมื่อมีโค้ดที่รันได้แล้ว                            |
| **เป้าหมาย**      | **ป้องกันบั๊ก** (*Prevent Defects*)           | **ค้นหาบั๊ก** (*Find Defects*)                           |

## 🪑 Case Study: ระบบจองเก้าอี้ไม้สำหรับทำงาน

* **โจทย์:** ลูกค้าต้องการ *"เก้าอี้ไม้สำหรับนั่งทำงาน"*
* **Verification (Pass):** QA ตรวจสอบแบบร่างแล้วพบว่า มี 4 ขาตามสเปก ใช้ชนิดไม้ตามที่กำหนด ความสูงตรงตามแบบเป๊ะ ➔ **ผลคือ ผ่านเงื่อนไขแบบร่าง**
* **Validation (Fail):** ลูกค้ามาลองนั่งทำงานจริงแล้วพบว่า *"มันแข็งเกินไป นั่งเกิน 30 นาทีแล้วปวดหลัง"* ➔ **ผลคือ ไม่ผ่าน เพราะไม่ตอบโจทย์การใช้งานจริง**

---

## 💡 Key Insights (ข้อคิดสำคัญสำหรับ QA)

* **Verification** ช่วยให้เราไม่หลงทางจากสเปก (ประหยัดค่าใช้จ่ายเพราะเจอจุดผิดพลาดตั้งแต่บนกระดาษ)
* **Validation** ช่วยให้เราไม่เสียเวลาสร้างโปรดักต์ที่ไม่มีใครอยากใช้
* **QA ที่ดีต้องทำทั้งสองอย่าง** ไม่ใช่แค่นั่งรอรัน Test โปรแกรมตอนท้ายเพียงอย่างเดียว!
