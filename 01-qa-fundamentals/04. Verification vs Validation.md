# 🔍 04. Verification vs Validation

> เข้าใจความแตกต่างระหว่างการตรวจสอบว่า Software ถูกสร้างตาม Spec หรือไม่ และ Software ตอบโจทย์ผู้ใช้จริงหรือไม่

---

# 🛠️ Verification

## "Are we building the product right?"

Verification คือการตรวจสอบว่า Software ถูกสร้างตาม Requirement และ Design ที่กำหนดไว้หรือไม่

เน้น:
- Requirement ถูกต้องหรือไม่
- Design ตรงตามที่วางไว้หรือไม่
- กระบวนการพัฒนาถูกต้องหรือไม่

เป็นการตรวจสอบแบบ **Static Testing**
(ไม่จำเป็นต้องรัน Software)

ตัวอย่าง:
- Requirement Review
- Design Review
- Code Review
- Inspection

---

# 🧪 Validation

## "Are we building the right product?"

Validation คือการตรวจสอบว่า Software ที่สร้างขึ้นสามารถตอบโจทย์ผู้ใช้และธุรกิจจริงหรือไม่

เน้น:
- ระบบทำงานตามที่ผู้ใช้ต้องการหรือไม่
- User สามารถใช้งานได้จริงหรือไม่
- Business Goal ถูกตอบสนองหรือไม่

เป็นการตรวจสอบแบบ **Dynamic Testing**
(ต้องมี Software ที่สามารถรันได้)

ตัวอย่าง:
- Functional Testing
- System Testing
- User Acceptance Testing (UAT)
- Usability Testing

---

# 📊 Verification vs Validation

| | Verification | Validation |
|-|-|-|
| คำถาม | Build the product right? | Build the right product? |
| ตรวจอะไร | Requirement, Design, Process | Software จริง |
| วิธี | Review / Inspection | Testing |
| เป้าหมาย | Prevent Defects | Find Defects |
| เวลา | เริ่มได้ตั้งแต่ต้น | หลังมี Software |

---

# 🪑 Case Study

Requirement: "สร้างระบบจองห้องประชุม"

🔹**Verification**
ตรวจสอบว่า:
- มีฟังก์ชันเลือกวันและเวลา
- มีจำนวนผู้เข้าร่วมตาม Requirement
- Flow การจองตรงตาม Design

ผล:
✅ Software ถูกสร้างตาม Spec


🔹**Validation**
ให้ User ทดลองใช้งานจริง
พบว่า:
- ขั้นตอนจองซับซ้อนเกินไป
- User หาเมนูจองไม่เจอ

ผล:
❌ ไม่ตอบโจทย์การใช้งานจริง

---

# 💡 Key Takeaways

- Verification = ตรวจว่าเราสร้าง Software ถูกตาม Spec หรือไม่
- Validation = ตรวจว่า Software ที่สร้างตอบโจทย์ผู้ใช้จริงหรือไม่
- QA ต้องทำทั้งสองด้าน ไม่ใช่แค่รัน Test หา Bug
- การตรวจสอบตั้งแต่ต้นช่วยลด Cost และ Risk
