# 🧠 05. Software Testing Principles

> หลักการพื้นฐานของ Software Testing ที่ช่วยให้ QA คิด วิเคราะห์ และตัดสินใจเกี่ยวกับการทดสอบได้อย่างมีเหตุผล

**Purpose:**

เข้าใจข้อจำกัดของการทดสอบซอฟต์แวร์ และเรียนรู้แนวคิดสำคัญที่ช่วยให้ QA สามารถวางแผน ออกแบบ และจัดลำดับความสำคัญของการทดสอบได้อย่างเหมาะสม

---

## 🎯 1. Testing shows presence of defects

การทดสอบช่วยให้เราค้นพบว่าระบบมีข้อบกพร่องอยู่จริงหรือไม่

แต่การทดสอบไม่สามารถพิสูจน์ได้ว่า **ระบบไม่มี Bug เลย** เพราะเราไม่สามารถทดสอบทุก Scenario ที่เป็นไปได้ทั้งหมด

> 💡 การทดสอบไม่ได้มีเป้าหมายเพื่อพิสูจน์ว่าซอฟต์แวร์สมบูรณ์แบบ แต่เพื่อค้นหาปัญหาที่อาจส่งผลกระทบต่อผู้ใช้งานและธุรกิจ

**Example:**

ระบบ Login ผ่าน Test Case 100 รายการ ไม่ได้หมายความว่า Login ไม่มี Bug ทุกกรณี

---

## ⚖️ 2. Exhaustive testing is impossible

ไม่สามารถทดสอบทุกอย่างได้ 100%

ในระบบจริงมีหลายปัจจัย เช่น:

- Input หลายรูปแบบ
- User behavior ที่แตกต่างกัน
- Environment ที่หลากหลาย
- Business rules ที่ซับซ้อน

ดังนั้น QA ต้องใช้แนวคิด **Risk-Based Testing**

โดยเลือกทดสอบส่วนที่:

- มีโอกาสเกิดปัญหาสูง
- มีผลกระทบต่อธุรกิจมาก
- มีความสำคัญต่อผู้ใช้งาน

---

## 💸 3. Early testing saves cost

การค้นพบ Defect ตั้งแต่ช่วงแรกของ Software Development Life Cycle (SDLC) ช่วยลดค่าใช้จ่ายและเวลาในการแก้ไข

QA ไม่ควรรอจน Development เสร็จแล้วค่อยเริ่ม Testing

QA สามารถมีส่วนร่วมตั้งแต่:

- Requirement Review
- Design Review
- Test Planning

เพื่อช่วยป้องกันปัญหาก่อนที่จะเกิดขึ้น

---

## 🧩 4. Defect clustering

Defect มักไม่ได้กระจายเท่า ๆ กันทั่วทั้งระบบ

ปัญหาส่วนใหญ่มักกระจุกอยู่ใน:

- ส่วนที่มี Logic ซับซ้อน
- Feature ที่เปลี่ยนแปลงบ่อย
- Module ที่มีความเสี่ยงสูง

**Example:**

ระบบ E-commerce:

- Payment
- Checkout
- User Account

มักมีความเสี่ยงมากกว่า Static Page ทั่วไป

ดังนั้น QA ควรให้ความสำคัญกับพื้นที่ที่มีความเสี่ยงสูงก่อน

---

## 🧪 5. Pesticide paradox

ถ้าเราใช้ Test Case เดิมซ้ำ ๆ โดยไม่ปรับปรุง อาจทำให้ไม่สามารถค้นพบ Defect ใหม่ได้

เหมือนแมลงที่เริ่มทนต่อยาฆ่าแมลง

ดังนั้น QA ควร:

- Review Test Case อย่างสม่ำเสมอ
- เพิ่ม Scenario ใหม่
- ใช้ Exploratory Testing เพื่อค้นหาปัญหาที่คาดไม่ถึง

---

## 🧭 6. Testing depends on context

วิธีการทดสอบที่เหมาะสมขึ้นอยู่กับประเภทและบริบทของระบบ

ตัวอย่าง:

**Banking Application**

- เน้น Security
- เน้น Accuracy
- เน้น Reliability

**Game Application**

- เน้น Performance
- เน้น User Experience
- เน้น Compatibility

ดังนั้นไม่มี Testing Strategy เดียวที่เหมาะกับทุก Product

---

## 🚫 7. Absence-of-errors is a fallacy

การที่ระบบไม่มี Bug ไม่ได้หมายความว่าระบบประสบความสำเร็จ

Software ที่ดีต้องตอบโจทย์:

- User ต้องการอะไร
- Business ต้องการอะไร
- ระบบใช้งานได้จริงหรือไม่

**Example:**

ระบบทำงานถูกต้อง ไม่มี Error

แต่ User ใช้งานยากจนไม่อยากใช้

ระบบนั้นก็ถือว่าไม่ประสบความสำเร็จ

---

# 🧠 Why this matters

Software Testing Principles ช่วยให้ QA เปลี่ยนจากการคิดแบบ:

> "ทำ Test Case ให้ครบ"

เป็น:

> "เลือกวิธีทดสอบที่เหมาะสม เพื่อค้นหาความเสี่ยงที่สำคัญที่สุด"

QA ที่ดีต้องสามารถคิดเกี่ยวกับ:

- ส่วนไหนมีความเสี่ยงสูงที่สุด?
- Feature ไหนส่งผลกระทบต่อ User มากที่สุด?
- ควรใช้เวลา Testing กับส่วนไหนก่อน?

---

# 💡 Key Takeaways

- Testing ช่วยค้นหา Defect แต่ไม่สามารถรับประกันว่าไม่มี Defect
- ไม่สามารถ Test ทุกอย่างได้ จึงต้องเลือก Test อย่างมีเหตุผล
- การค้นหา Defect เร็วช่วยลด Cost และ Risk
- Defect มักกระจุกในพื้นที่ที่ซับซ้อนหรือมีการเปลี่ยนแปลงบ่อย
- QA ต้องปรับปรุงวิธี Testing อยู่เสมอ
- Testing Strategy ต้องเหมาะกับ Context ของ Product
- Software ที่ไม่มี Bug ไม่ได้หมายความว่าจะประสบความสำเร็จ
